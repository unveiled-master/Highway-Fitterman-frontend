1. PROJECT IN ONE PARAGRAPH
----------------------------------------------------------------
An on-demand roadside mechanic and workshop marketplace for Ghana (brand: FixAm). The main
aim, in the owner's words, is stranded car owners whose car broke down on the way somewhere.
Roadside help leads; scheduled workshop booking is secondary. Customers request help, nearby
verified mechanics get offers, a mechanic quotes, the customer approves, payment is cash or
mobile money, and commission is tracked. There will be a web app and a mobile app, built
feature by feature from the owner's designs.

4. STANDING RULES (apply to all future work)
----------------------------------------------------------------
A. Project structure - the owner's instruction, verbatim:

   "For every project you create, use the structure and conventions of this repository as the
   starting point.

   First, inspect the repository's root files, package.json, and src/ tree. Treat the current
   project's structure as the reference, adapting it to the new project's framework and
   purpose rather than copying files or domain-specific code blindly.

   For a React + TypeScript + Vite frontend, follow this layout:

   - public/ - static files served as-is
   - src/assets/ - imported images and other assets
   - src/components/ - reusable UI components, grouped by purpose where useful (for example,
     forms/, modals/, datatables/, and contexts/)
   - src/data/ - static data, request definitions, and related data helpers
   - src/layout/ - shared page layouts
   - src/pages/ - route-level screens
   - src/pages/styles/ - page-specific CSS Modules
   - src/services/ - API clients and service logic
   - src/styles/ - shared styles
   - src/landing/ - landing-page UI and its components/styles, when the project has a landing page
   - src/App.tsx, src/main.tsx, src/App.css, and src/index.css - application setup and global styles

   Keep the root focused on project configuration and documentation, such as package.json,
   TypeScript and build configuration, lint configuration, index.html, .gitignore, and
   README.md. Use clear, consistent filenames and keep styles close to their related pages or
   components. Don't create empty folders or add categories the project does not need.

   Before adding a file, place it in the appropriate existing directory. If the project grows,
   extend the structure consistently instead of putting unrelated code into one large file.
   Preserve the project's existing conventions when working in an established repository, and
   explain any structural changes that are necessary.

   At the end, summarize the resulting structure and the purpose of any new folders."

B. Other standing instructions from the owner:
   - Use the LATEST version of every package (landing page instruction).
   - Build FEATURE BY FEATURE from the owner's designs.
   - Screens arrive as MOBILE designs: keep the mobile layout, derive a DESKTOP layout, and
     make everything responsive (instruction 10).
   - Follow docs/DESIGN.md for colours, type, spacing, shape and components. Prices are written
     "GH₵450.00" (no space) in Space Grotesk. Touch targets are at least 48px.
   - The web app and the mobile app are both planned.

C. Folder added beyond the owner's list: docs/ (this project's root) holds hand-off material:
   DESIGN.md, the original MVP report, and the design screenshots in docs/designs/.

8. KEY DECISIONS ALREADY MADE
----------------------------------------------------------------
 - Lead with ROADSIDE rescue; scheduled workshop booking comes later.
 - Customers: request first, account second. Phone OTP, no passwords.
 - Booking status and payment status are separate. Money is Decimal. Quotes are versioned.
   Commission rate is a setting, snapshotted per booking.
 - Mechanics see only coarse location until they accept a job (privacy).
 - SUPPORT staff can read; only ADMIN can change anything (approve, assign, settle, settings).
 - MVP cut list (deliberately NOT in the first release): subscriptions, workshop staff roles,
   in-app chat, automated matching beyond nearest-eligible, automated payouts, scheduled
   bookings, rich/itemised quotes, multi-country settings.
 - Lean MVP feature list: Customer - one-tap request, OTP at submit, inline vehicle info, live
   status, mechanic card + ETA + share link, call-out fee then quote approval, cash or MoMo,
   rating and report. Provider - signup + documents, online switch, job alerts, job screen,
   status updates, quote builder, record payment, "needs a tow". Admin - approve providers,
   live job board with manual assign, payments and commission, disputes, suspend.
 - Planned split: mobile app for providers (reliable alerts, background location) and
   customers; web for admin and a light customer request page; one shared API.

10. HOW TO RUN EVERYTHING
----------------------------------------------------------------
 Backend (mechanic-api):
   cp .env.example .env            # set secrets (32+ characters), ADMIN_PHONE
   docker compose up -d db
   npm install
   npx prisma migrate dev --name init
   npm run seed
   npm run start:dev               # http://localhost:3000/api/v1
   npm test
   In development, OTP codes are printed in the server log.

 Design-led frontend (this repo):
   npm install
   npm run dev                     # http://localhost:5173
   npm run build                   # run this first; it has not been run yet

 Prototype frontend (mechanic-web): npm install && npm run dev (proxies /api to port 3000).
